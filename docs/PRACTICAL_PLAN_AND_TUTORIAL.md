# 落地方案与操作教程

> 这份文档回答一个问题：**拿到这个仓库之后，从零到「QQ 群里的机器人会用技能、
> 有故障转移、账单看得见」，具体要做哪几步，每一步怎么验证它真的成了。**
>
> 它不重复其他文档的内容，而是把它们串成一条路径。每一节末尾给出「怎么确认这步
> 成了」——判据是**可观测的事实**（接口返回、界面数字、日志行），不是「点了保存
> 没报错」。区别很重要：本项目修过的绝大多数缺陷都属于「点了保存没报错，
> 但那个值从未生效」。

| 想让 AI 会用技能、MCP、Hook | [3. 让插件真的起作用](#3-让插件真的起作用) |

| 准备发版 | [6. 发布门禁](#6-发布门禁) |

命令约定：

- **Windows 后端**用 `.venv-win\Scripts\python.exe`；
  仓库里另有一个 `.venv`（Python 3.12），两者都可用，但**不要混用**——
  装在一个里的依赖另一个看不到。
- **WebUI** 用 `npm run test:unit`（`npm test` 这个脚本不存在）。
- Linux / VPS 用 `python3`。

## 1. 最小可用：一个能回话的机器人

### 1.1 装起来

```bash
# CentOS 9 / Ubuntu 22.04+
python3 -m venv .venv && . .venv/bin/activate
pip install -e .
python3 -m kirara_ai
```

首次启动会在 `data/` 下建目录、生成 `config.yaml`，并在日志里打印 WebUI 地址与
初始密码设置入口。

### 1.2 配一个上游模型

WebUI →「模型与 Agent → 模型」→ 添加供应商。最少填三项：适配器、API Key、
至少一个模型名。

### 1.3 怎么确认这步成了

**不要只看界面上有没有绿勾。** 打开「快速开始」页，它会显示一份**服务端自检**
（`GET /backend-api/api/system/readiness`，7 项），每项带可执行的处置建议。
要看的是这个，因为它是服务器真实状态，而不是浏览器里的点击痕迹。

```bash
curl -s -H "Authorization: Bearer <token>" \
  http://127.0.0.1:8080/backend-api/api/system/readiness | python3 -m json.tool
```

判据：`llm_backends_available` 为 `pass`。

> **一句必须知道的话**：如果这个接口读不到（服务没起、端口不对），
> 引导页会说明「暂时读不到自检结果」，而**不会**把任何一步标成已完成。
> 「不知道」和「未就绪」是两件事——把前者显示成后者，会让人去修一个不存在的问题。

## 2. 渠道接入：把消息真的收进来

四类渠道（OneBot / QQ 官方 / 企业微信 / Telegram）都在「机器人」页配置。
OneBot V11 适配器**已内置**，不需要装插件。

QQ 侧的完整操作（LLOneBot / PMHQ、扫码、反向 WebSocket、常见错误码）在
[`QQ_ONEBOT_OPERATIONS.md`](QQ_ONEBOT_OPERATIONS.md)。这里只讲验证。

### 2.1 怎么确认这步成了

自检里的 `im_adapters_available` 会把状态分成几类，**它们的处置完全不同**：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| `waiting` | 适配器在监听，上游还没连进来 | 查上游的反向 WS 地址与端口 |
| `reconnecting` | 上游刚掉线，仍在重连宽限期内 | **什么都不用做**，等它自己回来 |
| `credential_rejected` | 上游连上了，令牌被拒 | 改令牌，重试没有意义 |
| `qr_waiting_scan` | 连上了，但 QQ 还没登录 | 去扫码，**不要扫过期的旧二维码** |
| `storage_unavailable` | 链路正常，但落库在失败 | 查数据卷是否被只读重挂、磁盘是否写满 |

`reconnecting` 是这张表里**唯一一个不需要动手**的状态，也正是第 1 条问题
（compose 重启后 QQ 显示未连接）的答案：OneBot 实现掉了反向 WebSocket 会自己
回连，而「未连接」这个词会让人去重查地址与令牌——那两项从来没错。
宽限期由 `reconnect_grace_seconds` 控制（默认 45 秒），超时后转为 `disconnected`：
连着十分钟「正在重连」的链路就是断了，继续显示等待状态只是换个措辞掩盖故障。
填 `0` 关闭该状态。凭据被拒与握手被拒不会被它盖掉。

最后一类最隐蔽：**面板上一切正常，消息在丢**。卷在启动后被重新挂成只读时
WebSocket 仍然连着，适配器报 `connected`，而每一条要落库的投递都失败。

### 2.2 二维码总是过期怎么办

先在「机器人」页那一行点**刷新扫码状态**——它重读上游日志，给出最新一张码的
有效期、剩余秒数与文件路径。二维码有效期实测 120 秒，比「看一眼、去拿手机、
回来扫」这个动作序列短，所以屏幕上那张常常已经不是最新的。

按钮只做重读，**不让上游重新生成**：二维码由 LLOneBot / PMHQ 在自己的容器里
生成并在过期时自行重新请求。写成「重新生成」会让点了没反应的人去排查
Kirara，而要看的是上游容器。

看不到扫码信息时是没配日志路径，不是故障：在该适配器的
`qr_login_log_path` 里填上 OneBot 实现的日志文件路径（容器内路径）。
Telegram / 企业微信没有扫码环节，那一行不会出现这个按钮。

## 3. 让插件真的起作用

这是最容易「装了但没用上」的一环，所以判据写得最细。

### 3.0 一句话验证整条链：Agent 对话

「模型与 Agent → Agent 对话」页发一句话。**不需要在界面上挑任何插件**——
提示词、Skill、记忆、MCP、Hook 由「渠道身份 → Agent → 绑定」自动选中，
这是本项目的关系模型，四个入口（WebUI / QQ / Telegram / 企业微信）走的是同一条。

**怎么确认这步成了**（三项都要看，缺一项都可能是「看起来成了」）：

1. 有回复，且回复符合你绑定的提示词的语气与格式要求；
2. 「追踪 → 请求日志」里那一次请求的详情里，`tools` 列表包含你绑定的 MCP 工具；
3. 「资源」页那几条资源的状态列上**没有**「未生效」这个黄色标记——
   「已启用」不等于「生效」，一条没有被任何启用的 Agent 绑定的资源，
   启用了也进不了请求，那时状态列会同时显示「已启用」与「未生效」。

这条链有一组端到端测试守着
（`tests/web/api/llm/test_webui_chat_plugin_chain.py`）：它从 HTTP 请求进、
断言提示词进了 system 消息、MCP 工具出现在**第一轮**的工具清单里、工具结果回到了
第二轮的对话里、五个 Hook 事件真的触发、以及**未绑定的资源没有被带上**。

> **权限边界**：只有项目创建者能通过插件改动服务器内容或执行文件操作。
> 其他使用者仍然得到正常回复、提示词照常生效，但拿不到能操作服务器的工具，
> 命令型 Hook 也不会为他们起进程。这不是两套代码，而是同一条链上按
> Agent 属主与当前身份是否匹配决定的。

### 3.1 技能（Skill）

装法有四种：从 skills.sh 搜索安装、从 ZIP 安装、导入已有、从仓库发现。
都在「资源」页。

装多了怎么找回某一条：搜索框的匹配面是**名称、ID、描述与正文**四个。
正文这一面对提示词尤其重要——它的全部内容就是正文，而名称与描述只是随手填的一行字，
「哪一条里写了『先给结论』」只有搜正文答得上来。正文过滤在服务器侧做
（只读 prompt / memory / session；skill 与 hook 的正文是行为声明，不并进关键词搜索），
响应里**不含正文**：搜索是为了缩小清单，不是取回内容。

装错了怎么退回去，两条路径不要混：

| 我要 | 用哪个 | 边界 |
| --- | --- | --- |
| 回到上一个版本（内容还留着） | 资源详情的「回退到某版本」 | 需确认；回退后资源保持**停用**，等你审阅过再启用 |
| 彻底卸载（释放磁盘、释放 ID） | 资源详情的「卸载」 | 需确认；删前自动备份；**不可逆** |

「停用」不是卸载：它只让资源不生效，不释放磁盘、不清注册表，那个 ID 也不会重新可用
——想重装同名资源会撞「重复 ID」。要腾出 ID 必须真的卸载。

回退对**所有**资源类型可用。此前它要求资源先绑定工作流，而 skill / prompt / hook /
mcp / memory 从设计上就没有工作流绑定，于是这五类永远回退不了，报出的理由还是一句
与当前操作无关的「没绑定工作流」。

**装好之后必须做一件事：把它绑定到某个 Agent。** 只「启用」是不够的——
运行时遍历的是 `agent.skill_bindings`，不是「所有已启用的资源」。
资源列表会标出「未被任何 Agent 绑定」，那一栏就是为这件事存在的。

技能的生效方式是**渐进披露**，与主流 Agent 客户端同一原理：

- 带前置元数据（`name` + `description`）的技能 → 系统提示词里只放**一行目录**，
  正文由 `skill_<资源 id>` 工具在模型真的要用时取回；
- 没有前置元数据的纯文本技能 → 无法广告，仍整篇注入。

为什么不全部整篇注入：十个技能各 2000 token，就是**每一轮**固定多付 20000 token，
而其中绝大部分与当轮问题无关。更要紧的是，模型面对一堵墙时反而更容易忽略
其中的具体指令。

**怎么确认这步成了**：在「追踪 → 请求日志」里打开一次真实请求的详情，看它的
工具列表里有没有 `skill_<你的资源 id>`。有，就说明模型能调用它。

### 3.2 技能里的命令，服务器上装了没有

技能正文常常是一串命令（`agent-browser open ...`）。命令在不在服务器上，
由「资源 → 依赖」页记录。

**没装时最坏的表现不是报错，而是一个自信的假答案**：模型无从得知
`agent-browser` 不存在，只能把「我已经打开了浏览器」当成事实继续往下答，
而用户看不出与真的成功有什么区别。

因此依赖缺失时，技能的目录行与工具描述里会自动多一句「本技能依赖的服务器组件
当前不可用（…），不要假装已经执行过其中的命令」。三种状态严格区分：

| 依赖状态 | 提示 |
| --- | --- |
| 已就绪 | 不加任何字（多余的话是每轮都要付费的噪音） |
| 确认缺失 | 点名那个组件，并要求模型不要假装执行过 |
| 未探测 / 探测失败 / 未登记 | 同样什么都不说 |

最后一行是有意的：把「不知道」说成「缺失」会劝退一个本来能用的技能。

**怎么确认这步成了**：在依赖页对 `agent-browser-cli` 点「探测」，
它应显示 `ready`；未装时应显示 `missing` 并给出安装命令。

### 3.3 MCP

「MCP」页添加服务器。内置目录里有 `context7`（文档检索），一键安装。

**MCP 工具受两层门禁**：Agent 的 `mcp_allowlist`，以及创建者身份校验。
IM 渠道上的普通用户拿不到 MCP 工具——这是设计如此。
如果你希望自己在 QQ 上也能用，在「系统设置 → Agent 运行时 → 创建者渠道身份」
里声明你的渠道身份（等价于 `agent_runtime.creator_channel_identities`），
保存后重启服务。默认空表的含义是**聊天侧谁都拿不到，包括你本人**。

**怎么确认这步成了**：请求详情的工具列表里出现 `context7.resolve-library-id`。

**文件类 MCP 要多一步：给它一个可访问目录。** `filesystem` 装完之后
**没有任何可操作范围**——`npx` 起得来、握手成功、工具列得出，
而每次调用都因为没有允许的路径而失败。在「资源管理」列表里点这一行的
「运行时配置」，在「追加启动参数」里加上目录（例如 `/srv/data/docs`），保存。

配置入口在**资源管理**而不是 MCP 页：从目录装进来的 MCP 住在资源注册表里，
MCP 页的编辑表单只管 `config.yaml` 里手写的那些条目。命令与传输类型来自
已签名的资源包，两个页面都不允许改——那是摘要保护的身份。

### 3.4 Hook

Hook 挂在会话、工具、审计的生命周期事件上。内置 `hook.ai-debug` 用于调试。

**command 型 Hook 只有创建者能触发**，其他人的相同指令会被忽略——
但仍然返回正常的 AI 回复，不暴露「你没权限」这件事。

**每个 command 型 Hook 都是一个真进程**，因此它的 `timeout_ms`（内置那份是 5000）
要按「这台机器起一个 Python 要多久」来估，而不是按脚本自身的耗时。
内置 hook 一轮触发五个事件，本机实测合计约 0.6 秒；
如果你自己写的 Hook 命令要导入重依赖，把 `timeout_ms` 调大，
否则症状会是「hook 有时不触发」——超时后子进程被杀、该事件记成失败。

### 3.4.1 想看某个资源的正文写了什么

资源详情弹窗里有「入口正文」区块，只读。它旁边显示**摘要是否与版本记录一致**
——一致才说明你看到的与运行时载入的是同一份。多版本时可以切换看旧版，
回退前先看一眼旧版写了什么最实用。

正文**不能就地改**：内容摘要与清单绑定，运行时每次载入都重新校验，
就地改会让这个资源在下一次载入时失败（不是「改了没生效」，是彻底不可用）。
要改正文用同一个弹窗里的「上传 ZIP 升级」装一个新版本。

### 3.5 提示词与会话

内置 `prompt:office-research` 是一份中文办公/研究场景行为提示词。
会话在「模型与 Agent → Agent」页的「会话与待确认」区块：只显示计数与时间，
**不展示任何对话内容**。需要重置某个会话的上下文时清空历史即可，绑定关系不受影响。

**自己写一条提示词**：「资源管理」页工具栏的「新建提示词」——填 ID、类型、
名称、描述、正文，保存。打包与摘要由服务器完成，落盘后与内置条目同形。
可创建的类型只有三个（提示词 / 记忆 / 会话），因为它们的全部内容就是正文；
skill 的正文是给模型的行为说明、hook 是能起进程的命令声明、mcp 启用即拉进程，
那三类仍然走「打包 + 上传 + 显式确认」。

**改正文**：纯文本类型的那一行上有「编辑正文」图标。它保存的是一个**新版本**
而不是改原文件——`content_sha256` 把清单与文件绑在一起，就地改的后果不是
「改了没生效」，而是这个资源在下一次载入时直接失败。旧版本保留，改错了能回去；
版本号预填当前版本的下一个 patch（后端要求严格递增）。

**怎么确认这步成了**：保存后资源列表里出现这一条，状态是「未启用」并带
「需确认」——这是刻意的：提示词会进系统提示词、改变每一轮回复，
「保存即生效」会让一次手误立刻作用到所有对话上。点「启用」并确认，
再把它绑定到某个 Agent（只启用不绑定的效果是零，见 3.4 节）。

### 3.6 装 CLI 工具到 VPS

「资源 → 依赖」页可以把 rtk / graphify / memsearch 等装到服务器上。
命令由服务端固定，**浏览器只提交一个已登记的依赖 ID**，不接受任何路径或参数——
否则那就是一个远程命令执行接口。

`context-mode` 与 `caveman` 标为「Claude Code 插件」：它们装在**操作者自己的**
Claude 配置里，服务器侧无需也无法代为安装。界面上如实这么写，
而不是给一个永远失败的安装按钮。

## 4. 故障转移与超时

在「模型与 Agent → 模型」里，每个供应商可配：

- **优先级**（`priority`）：数值小的先用；
- **重试与失败阈值**：单家重试几次、连续失败几次开熔断；
- **三个超时**：流式首字节、流式静默、非流式整体；
- **熔断恢复**：恢复所需成功数、恢复等待、错误率阈值、最小请求数。

一个容易配错的地方：**重试和故障转移是两件事**。同一家重试 3 次与切换 3 家各试
1 次，在旧的 `attempt_count` 上都是 3，但处置相反——前者调超时与退避，
后者查供应商健康与熔断。统计里因此分成 `avg_retry_count` 与
`avg_failover_count` 两项。

**怎么确认这步成了**：把主上游的 Key 故意改错，发一条消息。
请求详情的「逐次尝试」表应显示：第一次 → 主上游、失败、错误类型；
第二次 → 备用上游、成功。**表里的顺序就是发生顺序**，否则「换到哪一家之后成功了」
无法回答。

### 4.0 上游只是抖了一下，怎么立刻把它放回队列
容错面板每一行都有「重置熔断」。它把该供应商清回 `closed` 并**同时撤销持久化的隔离**
（`data/llm/circuit-state.json` 里那条记录）。两件事必须一起做：

- 只清内存的话，下一次状态重建会从文件里把 open 原地读回来——按钮点了没反应，
  而日志里既没有错误也没有重置痕迹；
- 只删文件的话，本进程内仍在隔离期。

因此这是一个**创建者**动作并要求显式确认：它把一个刚被判定不健康的上游放回真实流量。
只重置你要放回的那一家——「取消所有隔离」会把其余正因真实故障被隔离的上游一起放行。

没有这个按钮时唯一的办法是等满恢复窗口，或者重启整个进程；而重启会一并中断所有
正在进行的对话。

### 4.0.1 队列顺序在哪里改

在「模型与 Agent → 容错状态」里，每条队列的每一行左侧有上移 / 下移两个按钮。
按一下就把这条队列的新次序整条提交给后端，页面直接换成后端返回的新状态。

**为什么不在供应商表单里填数字。** `priority` 是一个相对量，而供应商表单一次只看得见
一家：想把 P3 提到 P1，得先记住另外两家各是多少、再算一个中间值填进去，
而这三次编辑分散在三个表单里。数字仍然可以在表单里改（需要精确控制时用它），
但日常调顺序应该在**看得到队列的地方**做。

**为什么是按钮而不是拖拽。** 键盘可达是这套界面的硬要求；拖拽要额外补一套键盘操作
才能等价，而两套交互对同一件事时，出错很难判断是哪一套没生效。

三种会被拒绝的提交（都返回明确错误而不是尽力而为）：漏掉队列里的某一家、
出现队列外的名字、同一家出现两次。原因见
[`docs/OBSERVABILITY.md`](OBSERVABILITY.md) 的「在看到队列的地方改队列次序」。

**怎么确认这步成了**：按一下上移，页面上的 `P1`/`P2` 序号立刻交换，
并且行内 `priority` 数字也跟着换（不是新造两个数字，而是两家交换了原本的值）。
刷新页面后次序不变——变了说明只改了内存没落盘。

### 4.0.2 改了熔断参数，什么时候生效

保存即生效，不必重启，**包括编辑一个当前停用的后端**。

这一句值得单独写是因为它此前不成立：五个熔断参数只在熔断器被创建的那一刻被读进去，
而保存流程只在「后端原本启用且已加载」时才重建它。改一个停用后端的失败阈值会得到
一次「保存成功」，而下一次故障仍按旧阈值熔断——那个后端还不在容错面板的行里，
所以连「重置熔断」这个变通入口都没有。

刷新只换阈值，不动运行时状态：正在熔断的仍然熔断，在途请求数与已积累的成败样本
都保留。否则每次编辑任何一项配置都会顺手取消一次正在生效的隔离。

**怎么确认这步成了**：把某个停用后端的「失败阈值」从 8 改成 3 并保存，
再启用它并让上游连续失败 3 次——它应该在第 3 次就被隔离，而不是第 8 次。

### 4.0.3 改错了供应商配置，怎么退回上一版

在「模型与 Agent → 供应商」页顶部的工具条里，「导出配置 / 导入配置」旁边有
**「恢复上一版」**。它把供应商清单退回到**最后一次保存之前**的那一份。

每次写入配置前，服务器都会留一份 `config.yaml.bak`；这个按钮只从那份备份里取回
`llms.api_backends` 这一段。**不是整份配置回滚**——那会把你同一时间改过的 Web 端口、
IM 适配器、工作流一起退回去，而你要退的只是供应商。

确认框里写的是「最后一次保存的供应商改动将丢失」，包括新增、删除、Key 与容错参数。
这不是「找回旧版本」而是「丢掉最新一次」，两者方向相反，所以文案按后者写。

提示里会报两个数字：**恢复了几个、加载成功几个**。两者不等意味着有后端恢复进配置了
但起不来（Key 失效、地址不通、缺依赖）——只报一个数字会让这种情况看起来完全成功。

第一次保存供应商配置之前没有备份，这时按下去得到的是「还没有可恢复的备份」。
那是正常状态，不是故障。

**怎么确认这步成了**：删掉一个后端并保存，然后按「恢复上一版」——它回来了，
且行内的容错参数与凭据都在。再按一次不会回到更早的版本（只有一份备份）。

### 4.1 请求整流：有一类失败不该转移，该改一处重试

同一个供应商编辑页往下有五个整流开关（默认全开）。它们处理的是**换供应商也没用**
的那类失败——请求本身的参数在这个模型上不合法：

| 症状 | 上游报什么 | 整流做什么 |
| --- | --- | --- |
| 开了高推理强度，回复完全出不来 | `budget_tokens` / `thinkingBudget` 相关约束 | 把思考预算与最大输出长度调成一组合法值 |
| 换了模型之后多轮对话突然报错 | `Invalid 'signature' in 'thinking' block` | 移除上一轮已失效的思考块，正文保留 |
| 发图片给不支持图片的模型 | `does not support image` 一类措辞 | 图片换成可见占位文本，对话不中断 |
| 模型压根不支持思考 | `thinking is not supported by this model` 一类措辞 | 去掉整个思考配置再重试一次 |
| 配了推理强度，兼容网关直接拒 | `Unrecognized request argument: reasoning_effort` | 去掉该字段再重试一次 |

这几种情况下故障转移帮不上忙：备用上游收到同一个不合法的请求，同样会拒。
（最后一项只在错误里**同时**出现字段名与「不支持/不认识」类措辞时才动。
取值非法——上游只认 low/medium/high 而你配了最大强度——不会命中，
否则一个只需降档的请求会被整个删掉思考能力。）
整流只在**上游真的拒绝之后**动，只改命中白名单的那一处，每类只改一次；
改完仍失败就把原始错误抛出来。

**图片降级要单独说一句**：它是唯一会改变模型看到内容的一项。图片被换成
`[Unsupported Image]` 而不是删掉——删掉的话模型会对着空内容编一个答案，
而你以为它真看过那张图。如果你的部署里图片必须原样送达（宁可失败也不要降级），
就把这一项关掉，另外两项不受影响。

**怎么确认这步成了**：给一个不支持视觉的模型发一张图。
日志里应出现 `整流器改写请求后重试：media_fallback`，且回复里模型明确说
自己没收到图片，而不是凭文字猜内容。

### 4.2 离线部署：把自动版本探测关掉

「系统设置 → 下载源 → 禁用自动检查」。内网或离线机器上，版本探测每次都要等
PyPI 与 npm 各超时一次——启动时一次，**每打开一次 WebUI 还有一次**。
打开这个开关后两处都不再发请求。

同一页的「立即检查更新」按钮不受影响，它带 `?manual=1`。也就是说这个开关是
「不自动去外网」，不是「不能查更新」——需要时点一下照样能查。

### 4.3 上游还剩多少：在撞上限之前就知道

容错面板每一行都有「上游余量」。它读的是上游在每个响应里带回来的限额头，
不需要额外配置：

- `请求 12 (1%)` —— 还能发 12 次，占配额的 1%，该立刻降频；
- `Token 79,000 (98%)` —— Token 充裕；
- `8s 后重置` —— 等一会儿就好，不用改任何东西；
- `未上报` —— 这个上游不返回限额头（很多兼容端点如此），不是「余量为零」。

**「未上报」和 0% 是两件事**，界面上不会混。0% 表示余量真的用尽，是最该处置的
状态；把「没上报」显示成 0 会让你去排查一个不存在的紧急情况。

请求数与 Token 分开显示，因为它们会分别见底且处置相反：请求数见底要降低发送频率，
Token 见底要缩短上下文（减少历史轮数或改小 `max_tokens`）。

**怎么确认这步成了**：给一个真实上游发几条消息，回到容错面板。
若该上游返回限额头，「上游余量」会显示具体数字并随请求下降；显示「未上报」
说明这家不提供这些头——那是上游的选择，不是本项目的缺失。

## 5. 用量、成本与排查

### 4.4 回复怎么取回来：三档，按 Agent 和按渠道分别配

`reply_stream_mode` 有三档，优先级是 **Agent 声明 > 渠道默认 > 进程默认**：

| 档 | 上游取回方式 | 用户看到什么 | 什么时候用 |
| --- | --- | --- | --- |
| `off` | 非流式一次取回 | 等待，然后一条完整回复 | 上游很快、不需要首字节超时保护 |
| `aggregate` | 流式取回，服务端聚合 | 同上（**仍然是一条完整回复**） | 上游慢或不稳，要首字节超时、静默超时与首字节前故障转移 |
| `incremental` | 流式取回，边取边推 | **文字逐段出现** | 渠道能改写已交付内容（Telegram、WebUI 在线对话） |

两件容易搞错的事：

- **`aggregate` 不是「用户能看到流式」。** 它买到的是超时保护与故障转移可观测性；
  用户端仍然是一条完整消息。要用户看得见，必须是 `incremental`，且渠道能改写已经
  交付出去的内容。
- **`incremental` 由渠道能力决定，不是所有渠道都能兑现。** 能兑现的两个：
  **Telegram**（`editMessageText` 反复改写同一条消息）与 **WebUI 的在线对话**
  （`POST /backend-api/api/llm/chat/stream` 送 SSE，一条 `delta` 事件就是一次追加,
  界面右上角有「流式 / 非流式」开关）。QQ / OneBot 与企业微信没有等价能力，
  配了 `incremental` 会自动退回 `aggregate`——不报错，但也不会逐段显示。

**带工具的 Agent 也走流式。** 早前的实现是「凡是带工具的请求都不流式」，
而工具在第 0 轮就已经拼好（MCP + 队友 + 技能），于是一个绑了 MCP 的 Agent
（本项目的主流用法）**永远**拿不到首字节超时、静默超时与首字节前的故障转移。
现在判据改成适配器能力：OpenAI 兼容那一族的流式解析会累积 `delta.tool_calls`，
因此带工具也能流式；Claude / Gemini / Ollama 目前只解析文本增量，
带工具时仍走非流式（工具调用完整，只是少了那三项保护）。
这个能力按**该模型的全部候选供应商**取最弱的一个——故障转移会在候选之间切换，
只有第一家支持的话，一次转移之后工具调用就静默消失了。

按渠道配的典型写法：

```yaml
agent_runtime:
  reply_stream_mode: off          # 进程默认
  channel_reply_stream_modes:
    telegram: incremental          # 编辑已发出的那条消息
    onebot: aggregate              # QQ 没有等价能力，配 incremental 也会退回这一档
```

`webui` 不写也会走 SSE：那条路由本身就是按流式协议接住回复的，因此「客户端已经打开
了一条流」本身就是一次 `incremental` 声明——它的优先级在 Agent 与渠道**之后**、
进程默认之前，所以上面把进程默认写成 `off` 不会关掉 WebUI 的流式。真要关掉就写
`webui: off`（反向代理关掉分块传输、需要确认问题不在项目侧时用得上）。

单个 Agent 可以再覆盖它，入口在「Agent 管理 → 回复取回方式」，也可以走
`PUT /backend-api/api/agents/<agent_id>` 的 `reply_stream_mode` 字段。
Agent 上缺省是 `inherit`，即跟随渠道与进程默认——升级不会改掉既有 Agent 的行为。
**写错的值一律当作「跟随上层」，不会被当成开启**：一处笔误不该静默改变整条取回路径。

三层都会落盘。这一点值得单独确认：早前 Agent 那一层只在内存里生效，重启之后悄悄
变回 `inherit`，而界面上没有任何痕迹——一个重启即丢的配置项比没有这个配置项更糟。

**怎么确认这步成了**：在 Telegram 上配 `incremental`，发一条需要长回答的消息。
应先看到「正在生成回复…」，随后同一条消息被反复改写，最终内容与整段投递逐字一致。
**并且只有那一条消息**：增量收尾之后不会再补一条完整回复——两条内容逐字相同的
回复会让人以为机器人重复发送，那比不做增量更糟。
若只看到一条完整回复，检查该渠道的解析结果与 `execute_stream` 是否可用。

「追踪 → 使用统计」。三件事在这一页：

### 5.1 Token 不是一个数字

概览同时给总量与**输入 / 输出 / 缓存读 / 缓存写**四类，外加**缓存命中率**。

为什么必须分开：输入 Token 的单价通常是缓存读取的 5~10 倍。一份「总 Token
完全没变」的账单，在命中率从 80% 掉到 0% 时成本会翻几倍——而只看总量的页面，
这两种情况显示的数字**一模一样**。

`null` 与 `0` 在这里是两件事，界面也分开显示：

- 缓存显示「未上报」= 这些上游没返回缓存用量，命中率**未知**；
- 显示 `0` = 上游报了，确实没命中。

前者要查上游是否返回 usage（很多兼容端点根本不报这个字段），
后者才该去查提示词前缀是否稳定。

### 5.2 成本按天看，币种不相加

日成本曲线回答「这个月贵了三倍，是哪天开始的」。**每个币种一条线**——
把两种货币加进同一条曲线得到的是一串没有单位的数字，而它不会报错。

未定价请求单独标注。按 0 元并入当天合计，会把「有请求没匹配到价格版本」
显示成「这天便宜」。

历史账单**不会**被后来的改价改写：每条请求在完成时冻结一份价格快照。

**单次成本比合计成本更能指导换模型。** 模型与供应商两张图的 tooltip 里都有
「单次成本」。合计成本回答不了「这个模型贵不贵」：请求量最大的模型往往不是最贵的，
合计高也可能只是因为调用多。两个模型合计相同、单次差十倍时，只看合计完全看不出
差别。分母是**已定价**的请求数——把未定价的算进分母会得到一个偏低且看起来正常的
数字，而没有任何迹象表明它被稀释过。全部未定价时显示「无数据」，不显示 0
（0 是「不花钱」这个论断，事实是「还没配定价」）。

### 5.3 谁在失败

`error_categories` 回答「在失败什么」，但一个 `timeout` 分组里可能混着三家供应商。
所以 Provider / 模型分组各自带成功率——**那才是调故障转移队列顺序的依据**。

`pending` 不进成功率分母（还在跑的请求既不是成功也不是失败）；
一条都还没有结论时显示「未知」而不是 0%，否则一家刚配好、只有一条在途请求的
供应商会看起来是最差的那个。

### 5.4 时间范围预设

除日历选择器外有今天 / 近 24 小时 / 近 7 / 14 / 30 天。两点值得知道：

- 「今天」与「近 24 小时」不是同一个问题：上午九点时前者只覆盖 9 小时；
- 多天预设从**当天零点**起算，不是「now 减 7×24 小时」——后者首尾各半天，
  趋势图第一根柱子永远偏低，会被读成「那天用量下降」。

日界按**你选的时区**算，不是浏览器时区。跨时区对账时这一点是必需的。

### 6.1 本机跑不出来的四件事

## 7. 一页速查

| 我想确认… | 看哪里 |
| --- | --- |
| 服务真的就绪了吗 | `GET /system/readiness`，或「快速开始」页的自检面板 |
| QQ 到底连上没有 | 自检里的 `im_adapters_available` 分类状态；`initializing` 表示上游还在冷启动 QQ、`reconnecting` 表示等它自己回来（第 2.1 节） |
| 重启后 QQ 一直「正在启动」 | 正常，QQ 冷启动加登录实测超过 90 秒；宽限期默认 180 秒，超过才转「等待连接」 |
| 二维码总是过期 | 「机器人」页那一行的「刷新扫码状态」；标签里的剩余秒数会自己倒数，归零后改口（第 2.2 节） |
| 总时间预算 / 取回档位 / 工具阈值在哪配 | 「系统设置 → Agent 运行时」，改完重启生效 |
| 某个 Agent 单独要真流式 | 「Agent 管理 → 回复取回方式」选「逐步推送」；三层优先级里它最高（第 4.4 节） |
| 系统显示成功但 QQ 很久才收到 | 看投递时间线的 `send_seconds`；多页回复的页间节流有总额上界（默认 6 秒），超出说明是网络而不是节流 |
| 服务器上已经放好的资源包怎么装 | 「资源」页的「服务器上的包」，扫 `resources/imports` 目录 |
| 这个提示词/技能正文到底写了什么 | 资源详情弹窗的「入口正文」（只读，带摘要核对，第 3.4.1 节） |
| 技能真的会被用到吗 | 请求详情的工具列表里有没有 `skill_<id>` |
| 技能里的命令装了没有 | 「资源 → 依赖」页点「探测」 |
| 装错的资源怎么退回去 | 回退到某版本（内容还在）或卸载（释放 ID 与磁盘），第 3.1 节 |
| 文件类 MCP 连上了但什么都读不到 | 它还没有可访问目录：资源列表那一行的「运行时配置 → 追加启动参数」（第 3.3 节）|
| 受管 MCP 为什么在 MCP 页改不了 | 从目录装的住在资源注册表里，MCP 页只管 `config.yaml` 里手写的条目（第 3.3 节）|
| 点了「更新」提示没有 pip | 该环境由 uv 创建（默认不装 pip）。按提示用 `uv pip install --upgrade kirara-ai` 手动升级；检查发生在下载之前，不会白下几十 MB |
| 上游只是抖了一下，怎么马上放回队列 | 容错面板的「重置熔断」（第 4.0 节） |
| 代码怎么复制走 | WebUI 与 Telegram 的代码框旁有复制按钮；QQ / 企业微信是代码单独成条、长按整段复制 |
| 用户能不能看到文字逐段出现 | 只有 `incremental` + 支持编辑的渠道（目前 Telegram）；`aggregate` 仍是一条完整回复（第 4.4 节） |
| 工具太多，每轮都很贵 | 「资源 → MCP」工具数超过 12 时自动改用目录 + `search_tools`；阈值见 `agent_runtime.tool_search_threshold` |
| 故障转移生效了吗 | 请求详情的「逐次尝试」表 |
| 换供应商也没用的失败怎么办 | 供应商编辑页的五个整流开关（第 4.1 节） |
| 离线机器每次开页面都卡一下 | 「下载源 → 禁用自动检查」（第 4.2 节） |
| 这家上游还能发几次 | 容错面板的「上游余量」（第 4.3 节） |
| 这个模型到底贵不贵 | 模型图 tooltip 的「单次成本」（第 5.2 节） |
| 这个月钱花在哪 | 使用统计的日成本曲线 + 模型分组成本 |
| 成本一栏为什么是空的 | 先看该请求的 `usage_source`：`unknown` 是上游没回报用量，与「没配定价」是两件事。上游只回报部分维度（多数 OpenAI 兼容接口不报缓存写入量）时，缺失维度按 0 计价，总额照常算得出来 |
| 为什么这条回复慢 | 请求详情的首字节、总耗时 + 投递时间线 |
| 版本一致吗 | `python3 scripts/version.py check` |
| 界面提示的「新版本」比我装的旧 | 已修：预发布序号按数值比较。若仍出现，先确认 `VITE_APP_VERSION` 是真实构建注入值而非 `unknown` |
| 一次 Ctrl+Z 撤销得太多或太少 | 一次连续手势（拖拽、连续输入）= 一个检查点；批量操作（自动排布、复制多节点）= 一个检查点。第 6 节的门禁命令跑完即可验证 |
