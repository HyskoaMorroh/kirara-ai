# 落地方案与操作教程

> 这份文档回答一个问题：**拿到这个仓库之后，从零到「QQ 群里的机器人会用技能、
> 有故障转移、账单看得见」，具体要做哪几步，每一步怎么验证它真的成了。**
>
> 它不重复其他文档的内容，而是把它们串成一条路径。每一节末尾给出「怎么确认这步
> 成了」——判据是**可观测的事实**（接口返回、界面数字、日志行），不是「点了保存
> 没报错」。区别很重要：本项目修过的绝大多数缺陷都属于「点了保存没报错，
> 但那个值从未生效」。

## 1. 最小可用：一个能回话的机器人

### 1.1 装起来

```bash
# CentOS 9 / Ubuntu 22.04+
python3 -m venv .venv && . .venv/bin/activate
pip install -e .
python3 -m kirara_ai
```

首次启动会在 `data/` 下建目录、生成 `config.yaml`，并在日志里打印 WebUI 地址与
初始密码设置入口。

### 1.2 配一个上游模型

WebUI →「模型与 Agent → 模型」→ 添加供应商。最少填三项：适配器、API Key、
至少一个模型名。

### 1.3 怎么确认这步成了

**不要只看界面上有没有绿勾。** 打开「快速开始」页，它会显示一份**服务端自检**
（`GET /backend-api/api/system/readiness`，7 项），每项带可执行的处置建议。
要看的是这个，因为它是服务器真实状态，而不是浏览器里的点击痕迹。

```bash
curl -s -H "Authorization: Bearer <token>" \
  http://127.0.0.1:8080/backend-api/api/system/readiness | python3 -m json.tool
```

判据：`llm_backends_available` 为 `pass`。

> **一句必须知道的话**：如果这个接口读不到（服务没起、端口不对），
> 引导页会说明「暂时读不到自检结果」，而**不会**把任何一步标成已完成。
> 「不知道」和「未就绪」是两件事——把前者显示成后者，会让人去修一个不存在的问题。

## 2. 渠道接入：把消息真的收进来

四类渠道（OneBot / QQ 官方 / 企业微信 / Telegram）都在「机器人」页配置。
OneBot V11 适配器**已内置**，不需要装插件。

QQ 侧的完整操作（LLOneBot / PMHQ、扫码、反向 WebSocket、常见错误码）在
[`QQ_ONEBOT_OPERATIONS.md`](QQ_ONEBOT_OPERATIONS.md)。这里只讲验证。

### 2.1 怎么确认这步成了

自检里的 `im_adapters_available` 会把状态分成几类，**它们的处置完全不同**：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| `waiting` | 适配器在监听，上游还没连进来 | 查上游的反向 WS 地址与端口 |
| `credential_rejected` | 上游连上了，令牌被拒 | 改令牌，重试没有意义 |
| `qr_waiting_scan` | 连上了，但 QQ 还没登录 | 去扫码，**不要扫过期的旧二维码** |
| `storage_unavailable` | 链路正常，但落库在失败 | 查数据卷是否被只读重挂、磁盘是否写满 |

最后一类最隐蔽：**面板上一切正常，消息在丢**。卷在启动后被重新挂成只读时
WebSocket 仍然连着，适配器报 `connected`，而每一条要落库的投递都失败。

## 3. 让插件真的起作用

这是最容易「装了但没用上」的一环，所以判据写得最细。

### 3.1 技能（Skill）

装法有四种：从 skills.sh 搜索安装、从 ZIP 安装、导入已有、从仓库发现。
都在「资源」页。

**装好之后必须做一件事：把它绑定到某个 Agent。** 只「启用」是不够的——
运行时遍历的是 `agent.skill_bindings`，不是「所有已启用的资源」。
资源列表会标出「未被任何 Agent 绑定」，那一栏就是为这件事存在的。

技能的生效方式是**渐进披露**，与 cc-switch / Claude Code 同一原理：

- 带前置元数据（`name` + `description`）的技能 → 系统提示词里只放**一行目录**，
  正文由 `skill_<资源 id>` 工具在模型真的要用时取回；
- 没有前置元数据的纯文本技能 → 无法广告，仍整篇注入。

为什么不全部整篇注入：十个技能各 2000 token，就是**每一轮**固定多付 20000 token，
而其中绝大部分与当轮问题无关。更要紧的是，模型面对一堵墙时反而更容易忽略
其中的具体指令。

**怎么确认这步成了**：在「追踪 → 请求日志」里打开一次真实请求的详情，看它的
工具列表里有没有 `skill_<你的资源 id>`。有，就说明模型能调用它。

### 3.2 技能里的命令，服务器上装了没有

技能正文常常是一串命令（`agent-browser open ...`）。命令在不在服务器上，
由「资源 → 依赖」页记录。

**没装时最坏的表现不是报错，而是一个自信的假答案**：模型无从得知
`agent-browser` 不存在，只能把「我已经打开了浏览器」当成事实继续往下答，
而用户看不出与真的成功有什么区别。

因此依赖缺失时，技能的目录行与工具描述里会自动多一句「本技能依赖的服务器组件
当前不可用（…），不要假装已经执行过其中的命令」。三种状态严格区分：

| 依赖状态 | 提示 |
| --- | --- |
| 已就绪 | 不加任何字（多余的话是每轮都要付费的噪音） |
| 确认缺失 | 点名那个组件，并要求模型不要假装执行过 |
| 未探测 / 探测失败 / 未登记 | 同样什么都不说 |

最后一行是有意的：把「不知道」说成「缺失」会劝退一个本来能用的技能。

**怎么确认这步成了**：在依赖页对 `agent-browser-cli` 点「探测」，
它应显示 `ready`；未装时应显示 `missing` 并给出安装命令。

### 3.3 MCP

「MCP」页添加服务器。内置目录里有 `context7`（文档检索），一键安装。

**MCP 工具受两层门禁**：Agent 的 `mcp_allowlist`，以及创建者身份校验。
IM 渠道上的普通用户拿不到 MCP 工具——这是设计如此。
如果你希望自己在 QQ 上也能用，需要在
`agent_runtime.creator_channel_identities` 里声明你的渠道身份。

**怎么确认这步成了**：请求详情的工具列表里出现 `context7.resolve-library-id`。

### 3.4 Hook

Hook 挂在会话、工具、审计的生命周期事件上。内置 `hook.ai-debug` 用于调试。

**command 型 Hook 只有创建者能触发**，其他人的相同指令会被忽略——
但仍然返回正常的 AI 回复，不暴露「你没权限」这件事。

### 3.5 提示词与会话

内置 `prompt:office-research` 是一份中文办公/研究场景行为提示词。
会话在「模型与 Agent → Agent」页的「会话与待确认」区块：只显示计数与时间，
**不展示任何对话内容**。需要重置某个会话的上下文时清空历史即可，绑定关系不受影响。

### 3.6 装 CLI 工具到 VPS

「资源 → 依赖」页可以把 rtk / graphify / memsearch 等装到服务器上。
命令由服务端固定，**浏览器只提交一个已登记的依赖 ID**，不接受任何路径或参数——
否则那就是一个远程命令执行接口。

`context-mode` 与 `caveman` 标为「Claude Code 插件」：它们装在**操作者自己的**
Claude 配置里，服务器侧无需也无法代为安装。界面上如实这么写，
而不是给一个永远失败的安装按钮。

## 4. 故障转移与超时

在「模型与 Agent → 模型」里，每个供应商可配：

- **优先级**（`priority`）：数值小的先用；
- **重试与失败阈值**：单家重试几次、连续失败几次开熔断；
- **三个超时**：流式首字节、流式静默、非流式整体；
- **熔断恢复**：恢复所需成功数、恢复等待、错误率阈值、最小请求数。

一个容易配错的地方：**重试和故障转移是两件事**。同一家重试 3 次与切换 3 家各试
1 次，在旧的 `attempt_count` 上都是 3，但处置相反——前者调超时与退避，
后者查供应商健康与熔断。统计里因此分成 `avg_retry_count` 与
`avg_failover_count` 两项。

**怎么确认这步成了**：把主上游的 Key 故意改错，发一条消息。
请求详情的「逐次尝试」表应显示：第一次 → 主上游、失败、错误类型；
第二次 → 备用上游、成功。**表里的顺序就是发生顺序**，否则「换到哪一家之后成功了」
无法回答。

### 4.1 请求整流：有一类失败不该转移，该改一处重试

同一个供应商编辑页往下有四个整流开关（默认全开）。它们处理的是**换供应商也没用**
的那类失败——请求本身的参数在这个模型上不合法：

| 症状 | 上游报什么 | 整流做什么 |
| --- | --- | --- |
| 开了高推理强度，回复完全出不来 | `budget_tokens` 相关约束 | 把思考预算与最大输出长度调成一组合法值 |
| 换了模型之后多轮对话突然报错 | `Invalid 'signature' in 'thinking' block` | 移除上一轮已失效的思考块，正文保留 |
| 发图片给不支持图片的模型 | `does not support image` 一类措辞 | 图片换成可见占位文本，对话不中断 |

这三种情况下故障转移帮不上忙：备用上游收到同一个不合法的请求，同样会拒。
整流只在**上游真的拒绝之后**动，只改命中白名单的那一处，每类只改一次；
改完仍失败就把原始错误抛出来。

**图片降级要单独说一句**：它是唯一会改变模型看到内容的一项。图片被换成
`[Unsupported Image]` 而不是删掉——删掉的话模型会对着空内容编一个答案，
而你以为它真看过那张图。如果你的部署里图片必须原样送达（宁可失败也不要降级），
就把这一项关掉，另外两项不受影响。

**怎么确认这步成了**：给一个不支持视觉的模型发一张图。
日志里应出现 `整流器改写请求后重试：media_fallback`，且回复里模型明确说
自己没收到图片，而不是凭文字猜内容。

### 4.2 离线部署：把自动版本探测关掉

「系统设置 → 下载源 → 禁用自动检查」。内网或离线机器上，版本探测每次都要等
PyPI 与 npm 各超时一次——启动时一次，**每打开一次 WebUI 还有一次**。
打开这个开关后两处都不再发请求。

同一页的「立即检查更新」按钮不受影响，它带 `?manual=1`。也就是说这个开关是
「不自动去外网」，不是「不能查更新」——需要时点一下照样能查。

### 4.3 上游还剩多少：在撞上限之前就知道

容错面板每一行都有「上游余量」。它读的是上游在每个响应里带回来的限额头，
不需要额外配置：

- `请求 12 (1%)` —— 还能发 12 次，占配额的 1%，该立刻降频；
- `Token 79,000 (98%)` —— Token 充裕；
- `8s 后重置` —— 等一会儿就好，不用改任何东西；
- `未上报` —— 这个上游不返回限额头（很多兼容端点如此），不是「余量为零」。

**「未上报」和 0% 是两件事**，界面上不会混。0% 表示余量真的用尽，是最该处置的
状态；把「没上报」显示成 0 会让你去排查一个不存在的紧急情况。

请求数与 Token 分开显示，因为它们会分别见底且处置相反：请求数见底要降低发送频率，
Token 见底要缩短上下文（减少历史轮数或改小 `max_tokens`）。

**怎么确认这步成了**：给一个真实上游发几条消息，回到容错面板。
若该上游返回限额头，「上游余量」会显示具体数字并随请求下降；显示「未上报」
说明这家不提供这些头——那是上游的选择，不是本项目的缺失。

## 5. 用量、成本与排查

「追踪 → 使用统计」。三件事在这一页：

### 5.1 Token 不是一个数字

概览同时给总量与**输入 / 输出 / 缓存读 / 缓存写**四类，外加**缓存命中率**。

为什么必须分开：输入 Token 的单价通常是缓存读取的 5~10 倍。一份「总 Token
完全没变」的账单，在命中率从 80% 掉到 0% 时成本会翻几倍——而只看总量的页面，
这两种情况显示的数字**一模一样**。

`null` 与 `0` 在这里是两件事，界面也分开显示：

- 缓存显示「未上报」= 这些上游没返回缓存用量，命中率**未知**；
- 显示 `0` = 上游报了，确实没命中。

前者要查上游是否返回 usage（很多兼容端点根本不报这个字段），
后者才该去查提示词前缀是否稳定。

### 5.2 成本按天看，币种不相加

日成本曲线回答「这个月贵了三倍，是哪天开始的」。**每个币种一条线**——
把两种货币加进同一条曲线得到的是一串没有单位的数字，而它不会报错。

未定价请求单独标注。按 0 元并入当天合计，会把「有请求没匹配到价格版本」
显示成「这天便宜」。

历史账单**不会**被后来的改价改写：每条请求在完成时冻结一份价格快照。

**单次成本比合计成本更能指导换模型。** 模型与供应商两张图的 tooltip 里都有
「单次成本」。合计成本回答不了「这个模型贵不贵」：请求量最大的模型往往不是最贵的，
合计高也可能只是因为调用多。两个模型合计相同、单次差十倍时，只看合计完全看不出
差别。分母是**已定价**的请求数——把未定价的算进分母会得到一个偏低且看起来正常的
数字，而没有任何迹象表明它被稀释过。全部未定价时显示「无数据」，不显示 0
（0 是「不花钱」这个论断，事实是「还没配定价」）。

### 5.3 谁在失败

`error_categories` 回答「在失败什么」，但一个 `timeout` 分组里可能混着三家供应商。
所以 Provider / 模型分组各自带成功率——**那才是调故障转移队列顺序的依据**。

`pending` 不进成功率分母（还在跑的请求既不是成功也不是失败）；
一条都还没有结论时显示「未知」而不是 0%，否则一家刚配好、只有一条在途请求的
供应商会看起来是最差的那个。

### 5.4 时间范围预设

除日历选择器外有今天 / 近 24 小时 / 近 7 / 14 / 30 天。两点值得知道：

- 「今天」与「近 24 小时」不是同一个问题：上午九点时前者只覆盖 9 小时；
- 多天预设从**当天零点**起算，不是「now 减 7×24 小时」——后者首尾各半天，
  趋势图第一根柱子永远偏低，会被读成「那天用量下降」。

日界按**你选的时区**算，不是浏览器时区。跨时区对账时这一点是必需的。

## 6. 发布门禁

版本只有一个来源：`pyproject.toml`。Python / npm / uv.lock / Docker / WebUI /
Actions / Tag / Release 文案都由它推导。

```bash
python3 scripts/version.py check     # 各处版本是否一致
python3 scripts/version.py get       # 当前版本
python3 scripts/version.py tag       # 对应的 tag 名
```

发版前必须全绿的四项：

```bash
.venv-win\Scripts\python.exe -m pytest tests -q    # 后端（Windows）
cd webui && npm run type-check && npm run test:unit
git diff --check                                    # 行尾与空白
python3 scripts/version.py check
```

### 6.1 本机跑不出来的四件事

以下四项**必须在真实环境验证**，任何本机结果都不能替代：

1. Docker Compose 重启后数据是否真的还在；
2. 真实 QQ 扫码登录与 PMHQ 链路；
3. 真实多上游的故障转移（本机只能验证逻辑，不能验证上游行为）；
4. 四类客户端里消息的真实渲染。

没有这四项证据时**不打 tag、不推镜像、不发 Release**。

### 6.2 镜像里不能有的东西

`docs/LOGO.jpg`（私有文件）、`PATHFINDER-2026-08-21/`、`.venv`、密钥、缓存、
测试临时产物。`.dockerignore` 已排除，但发版前值得再确认一次镜像体积没有异常增长。

## 7. 一页速查

| 我想确认… | 看哪里 |
| --- | --- |
| 服务真的就绪了吗 | `GET /system/readiness`，或「快速开始」页的自检面板 |
| QQ 到底连上没有 | 自检里的 `im_adapters_available` 分类状态 |
| 技能真的会被用到吗 | 请求详情的工具列表里有没有 `skill_<id>` |
| 技能里的命令装了没有 | 「资源 → 依赖」页点「探测」 |
| 故障转移生效了吗 | 请求详情的「逐次尝试」表 |
| 换供应商也没用的失败怎么办 | 供应商编辑页的四个整流开关（第 4.1 节） |
| 离线机器每次开页面都卡一下 | 「下载源 → 禁用自动检查」（第 4.2 节） |
| 这家上游还能发几次 | 容错面板的「上游余量」（第 4.3 节） |
| 这个模型到底贵不贵 | 模型图 tooltip 的「单次成本」（第 5.2 节） |
| 这个月钱花在哪 | 使用统计的日成本曲线 + 模型分组成本 |
| 为什么这条回复慢 | 请求详情的首字节、总耗时 + 投递时间线 |
