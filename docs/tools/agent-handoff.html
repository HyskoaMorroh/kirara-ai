会话中断 / 无损接续

Session Salvage

Codex 或 Claude Code 的会话被上游 400、供应商熔断、上下文超限打断时， 代码还在磁盘上，但进度、失败清单、环境教训只活在那段对话里。 这个脚本把它们从会话里搬进仓库，让新会话读文件而不是读你的复述。

agent-handoff.py
653 行 · 零依赖
Python 3.9+

本机 108 个转录说了什么

这套阈值不是猜的。脚本扫过本机全部 54 个 Claude Code 转录（101 MB）与 54 个 Codex rollout（33 MB）， 按体积分组统计「出现过致命错误」的会话比例。致命错误指 content-blocked、供应商全部熔断、图片超限—— 这三类会让会话再也无法继续，而不只是报个错。

横轴 = 该体积区间内出现过致命错误的会话占比

250 KB 以下无一例外全都干净，8 MB 以上无一例外全都出过事。 样本里最大的那个转录 18.6 MB、1890 行，同时命中了熔断、命令未找到、 文件未读、权限被拒四类错误。

样本量小（>8 MB 只有 4 个会话），所以这是经验阈值而非统计定律。 但方向足够明确：转录越大，越该趁早交接。

七千次工具调用的分布

同一次扫描顺带统计了工具使用。Bash 3748 次远超其他， Edit 1051、Read 1033、PowerShell 780， 总计 7253 次调用、339 次报错结果。这解释了转录为什么长得快 —— 每次命令的完整输出都留在里面。

体检模式

不确定该不该交接？用 --vitals 直接体检本机所有会话， 它不碰任何仓库，只读转录：

Claude Code 与 Codex 一起排，因为风险不分家 —— 两边都走同一个 cc-switch 代理、 同一批中转商。哪边先撞上熔断，另一边通常也快了。

体征表也会自动进交接文件。 跑 agent-handoff . 时它默认附一张表在「最近提交」之后， 这样新会话一眼就知道自己继承的是什么状态。 不想要就加 --no-vitals。

会话中断时，究竟丢了什么

代码没丢。真正只存在于对话里、关掉就没有的是这四样： 计划的完成状态、失败测试的具体名字、 踩过的环境坑、子代理还没回收的报告。 脚本抢救前三样——第四样一旦会话断掉就真的没了，这也是为什么要尽早固化。

STEP 01

提交快照

把未提交的改动落成一个 commit，让新会话能用 git log 分辨"哪些是上一轮改的"。不推送，纯本地。

自动排除计划文档里声明为「user-owned / 用户私有」的文件—— 它从约束段自己读，不靠你告诉它。

STEP 02

回填计划

按文件是否存在加符号是否已定义两类客观证据， 把计划文档的复选框勾回去。

不问模型"你觉得做完了吗"。文件在、符号在，才算完成； 缺一样就标为部分，缺口逐条列出。

STEP 03

生成交接

写一份交接 Markdown 进仓库：现场坐标、完成度表、失败清单、环境坑， 外加一段可直接粘贴的开场提示词。

提示词刻意只有十几行——让新会话去读文件， 而不是把交接内容重新灌回对话里。

一条命令

# 在任意 git 仓库根目录 agent-handoff . # 先看它打算做什么，不写任何文件 agent-handoff . --dry-run # 跳过测试，只要现场快照（最快） agent-handoff . --skip-tests # 换个项目，路径随便给 agent-handoff E:\output\some-other-project

先跑 --dry-run。 它会打印将要执行的 git 命令、将要勾选的步数、交接文件的前 40 行，但不落盘。 确认无误再跑真的。

什么时候该跑它

本机数据给出了三个明确的触发点，按紧迫程度排：

看到 content-blocked
立刻。这不是暂时故障——上游拒绝的是该会话累积的内容， 换 provider、改配置、重试都一样被拒。实测同一分钟内新会话 200、老会话 400。 唯一的出路是弃用该会话。
「所有供应商已熔断」反复出现
这是本机最高频的致命签名，42 次分布在 6 个会话。一次抖动可能自愈， 但反复出现说明整个池子进入了自锁状态。先固化现场再排查代理。
转录超过 3 MB
预防性动作。此时还没坏，但已进入 33% 出事的区间； 越过 8 MB 就是 100%。趁能正常工作时交接，比出事后抢救干净得多。

完成度判定表

交接文件里最有价值的一张表。文件证据和符号证据都满格才判「完成」， 任何一项缺失都不会被当成做完：

Task 5 是个好例子：8 个文件全在，但 6 个应产出符号只找到 2 个 —— 判「部分」而不是「完成」，缺口明细会点名是哪 4 个符号没找到。 这比模型自我报告可靠得多。

它怎么知道你的项目 —— 全部靠推断

脚本里没有任何项目名、路径、任务名或测试命令。每一项都从仓库自己读出来：

分支 / HEAD / 未提交
git 元数据。没有 upstream 时退回 origin/main 再退回 origin/master 数领先提交。
计划文档在哪
递归找同时含「任务标题 + 3 个以上复选框」的 markdown，取最新修改的那个。跳过 node_modules、.venv、dist。
每个任务该产出什么
解析计划里的 Files: 段拿文件清单，Interfaces: Produces 段拿符号名。中英文关键词都认。
哪些文件不能提交
在约束段匹配「user-owned」「用户私有」「must not be staged」「不得提交」，取反引号里的路径，再校验它长得像路径而不是句子片段。
测试命令是什么
有 pyproject.toml 就找可用解释器（.venv-win → .venv → uv → 当前 Python）。前端读 package.json 的 scripts，按 test:unit → test → vitest → jest 顺序取实际存在的那个。
符号算不算已实现
先在该任务自己的文件里正则找定义，再退回 rg，rg 不在就用 git grep。三层降级。

为什么按 scripts 实际内容取测试命令。 真实案例：计划文档写着 npm --prefix webui test，但那个项目的 package.json 里脚本名是 test:unit，照抄计划会得到 Missing script: "test"。脚本读实际 scripts，所以不会踩这个坑， 而且会把这条差异写进交接文件的环境注意事项。

安装

两个文件，放进任何一个已在 PATH 上的目录。本机已装在 C:\Users\devin\bin\：

C:\Users\devin\bin\ ├─ agent-handoff.py # 主脚本，653 行，只用标准库 └─ agent-handoff.cmd # Windows 包装器，设好 UTF-8 再调 python

包装器存在的唯一理由是编码：Windows 上不设 PYTHONUTF8=1 时中文输出会撞上 GBK 编码错误。包装器内部注释刻意全用 ASCII —— .cmd 文件里的中文注释在 GBK 终端下会被当成命令执行。

Linux / macOS 直接调 python3 agent-handoff.py，或 chmod +x 后靠 shebang 运行，不需要包装器。

参数

repo
仓库路径，位置参数，默认当前目录。必须是 git 仓库——交接依赖 git 元数据，不是则直接报错退出。
--plan PATH
手动指定计划文档。省略则自动探测。项目里有多份候选文档时用它消除歧义。
--out PATH
交接文件输出路径。默认与计划文档同目录，命名 YYYY-MM-DD-handoff.md。
-m, --message
提交信息。省略则用 chore: 会话交接快照 <时间>。
--no-commit
只分析并生成交接文件，不碰 git。适合你想自己控制提交内容时。
--skip-tests
不跑测试。大项目全量测试要几分钟，急着开新会话时用这个。
--test-timeout N
单条测试命令超时秒数，默认 900。超时记为 <timeout> 而不是崩掉。
--vitals
只体检本机会话转录并退出，不碰任何仓库。不确定该不该交接时先跑这个。
--no-vitals
交接文件里不含体征表。默认是含的。
--dry-run
全程只打印将要做什么，不写任何文件、不提交、不改计划。

三条设计约束

不硬编码

唯一的常量是格式约定——markdown 复选框、Files: 段、 Interfaces: Produces 段。这些是 superpowers 计划模板的通用结构，不是某个项目的知识。 换成别的项目、别的语言、别的任务编号，照样能跑。已在一个合成的 Python 小项目上验证过：正确识别 2 个任务、勾对 1 个、点名缺失的 src/report.py 和 build_report、并排除了受保护的 assets/brand.png。

失败不中断

每个外部命令都包在 run() 里，超时、命令不存在、任何异常都返回 (code, 说明文本) 而不抛出。rg 不在就退回 git grep；uv 不在就用当前 Python；测试跑不起来就把输出末两行记进交接文件。 宁可给一份带缺口的交接，也不要因为一个工具缺失而什么都不产出。

提示词要短

生成的开场提示词只有十几行，只包含定位信息和优先级。 交接细节全在仓库文件里，让新会话自己去读。 上一个会话就是因为上下文累积到 114k+ tokens 之后被上游拒绝的—— 把交接内容重新灌进对话，等于原地重演那次死亡。

它不做什么

不推送。生成的提交停在本地，要不要上远程由你决定。

不猜测。判定完成只看文件在不在、符号有没有定义，不做语义推断。 一个空文件也会被算成「文件存在」——这是有意的取舍：宁可偶尔偏乐观， 也不要引入需要模型判断的环节。

不回收子代理报告。子代理的输出只在会话进程里，会话一断就没了。 唯一的对策是让子代理把结论直接写进文件，而不是只回报给主线。
