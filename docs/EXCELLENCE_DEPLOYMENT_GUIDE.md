# 精湛部署与扩展指南

本文面向要把 Kirara AI 3.3.0b16 部署给真实用户的维护者。目标是让首次部署、模型配置、内置工作流、规则触发和画布编辑都能被看懂、复现和排错。

## 先说边界

- 本版本保留了既有的模型下拉手动选择、最多四个备用模型、自动定期探测、内置工作流、调度规则、插件和 MCP 管理能力。
- 自动探测只更新后端可用模型目录，不会替用户改写工作流中已经选定的主模型或备用模型。探测后，请在原有下拉框中主动确认模型选择。
- 本版本已有 extension manifest、capability、允许列表 lifecycle 和脱敏审计，但 Agent/Skill 仍只是现有工作流与 catalog 元数据的组合，不是新运行时；Hook 也不是 Python sandbox。真实边界见 [Agents、Skills、Hooks 与 MCP 实用指南](AGENTS_SKILLS_HOOKS_MCP_GUIDE.md)。

## 首次部署的最短路径

1. 按 `docs/QUICKSTART.md` 完成首次登录和管理员密码设置。
2. 在模型页配置至少一个 LLM 后端。等待模型目录加载完成后，在工作流节点原有的下拉框中手动选择模型。
3. 打开“工作流模板”，从聊天、工具调用或对应业务模板开始，不要从空白画布硬搭第一条链路。
4. 打开“调度规则”，使用试运行功能输入一条示例消息，确认命中的规则、优先级、被前序规则截断的规则和不确定条件。
5. 发送一条真实但无敏感信息的测试消息，确认规则、工作流和模型串通。
6. 在进行任何恢复、导入、删除或大范围重排前，先创建完整备份。

旧实例升级必须先停止 A、制作独立数据目录副本，再让 B 读取副本；readiness、工作流/调度/模型核对和回滚顺序见 [升级指南](UPGRADING.md)。

## 画布操作基线

| 目标 | 使用方式 | 保护点 |
|---|---|---|
| 消除重叠 | 点击“自动排布”或使用 `Ctrl+L` | 只调整画布坐标，不改节点配置、模型选择或连线语义 |
| 看清全图 | 点击“适应画布” | 适合首次打开大工作流或排布后检查 |
| 快速定位 | 点击“查找节点”并输入节点名 | 避免在大图中滚动寻找 |
| 发现结构问题 | 点击“检查” | 预检只报告，不保存、不执行、不自动改图 |
| 管理代码节点端口 | 在节点配置侧栏增删端口 | 删除按钮有明确提示；先确认没有重要连线 |
| 窄屏操作 | 侧栏和四类弹窗会受视口宽度限制 | 保留左右安全边距，避免文本和按钮跑到屏幕外 |

画布会按 Vue Flow 的节点、边变更事件保存，而不是在每次选择或尺寸变化时序列化整张图。切换工作流或离开编辑器时，待处理的防抖写入会取消，避免旧图回写到新图。

## 内置模板与规则

运行时内置工作流共 13 份 YAML（均在 `data/workflows/chat/`），包内预设 11 份 YAML；代码另注册 6 条预设工作流（`game:dice`、`game:gacha`、`system:help`、`system:clear_memory`、`chat:normal`、`chat:memory_store`），其中 `chat:normal` 与 `chat:memory_store` 在存在同名 YAML 时由 YAML 生效（`register_preset_workflow` 遇到已注册的 ID 会跳过），因此纯 pip 安装且无 `data/workflows` 时这 6 条全部可用。默认调度规则为 8 条，按“优先级从高到低、同优先级按规则 ID 升序”判断，优先级 15 的 `game_gacha_mention` 也在文档和规则表中明确列出。

首次上线建议按以下顺序启用：

1. 先用通用聊天规则验证普通模型链路。
2. 再启用时间、抽卡或平台提及等特定触发规则，并通过试运行检查正则和优先级。
3. 最后接入需要 MCP、插件或多模型降级的工作流。

## 可靠性门禁

每次准备替换旧目录前，至少通过以下门禁：

| 门禁 | 目的 |
|---|---|
| Python 全量测试 | 验证 API、规则、工作流、备份和 MCP 回归 |
| WebUI 类型检查与生产构建 | 验证 Vue 模板、类型和打包 |
| 工作流预检 | 验证节点、端口、类型、入口、不可达节点和非受控环 |
| 规则试运行 | 验证优先级和条件组合，不实际发送消息 |
| 备份与恢复演练 | 验证故障时能回到可用状态 |
| Docker 构建和容器冒烟 | 验证与本地解释器无关的真实部署路径 |

不要在 Docker 构建和容器冒烟尚未通过时删除旧项目 A。应先保留 A 作为只读回滚源，完成一次 B 的备份、启动、登录、模型手动选择、规则试运行、真实消息和恢复演练后再归档。

## 后续精湛提升路线

### 第一阶段：可观测性

为工作流执行、模型请求、规则命中和插件调用增加统一的 trace ID；默认仅记录耗时、结果、错误类别和对象 ID，不记录提示词、回复正文或密钥。OpenTelemetry 的 Trace 由表示一次操作的 Span 组成，适合将“用户消息 -> 规则命中 -> 工作流 -> 模型调用”串成可检索的链路。

验收标准：慢工作流能看出耗时落在规则、节点、模型还是插件；异常能从 WebUI 跳到相同 trace ID 的日志；关闭开关后不创建额外遥测数据。

### 第二阶段：受控 Agents、Skills 与 Hooks

Agent 应由 Workflow、模型/工具/记忆策略和 DispatchRule 组合；Skill 应由 catalog 中的版本化模板、输入输出、前置条件和示例描述。两者都复用现有执行器和 Block 校验，不新增能绕过工作流边界的运行时。

Hook 只能使用真实允许列表：`startup_completed`、`shutdown_requested`、`workflow_before`、`workflow_after`、`workflow_error`、`dispatch_preview`、`model_catalog_refreshed`、`mcp_operation`。manifest 权限只约束注入的 host facade，插件仍是进程内 Python；不要加载不可信插件，也不要把 Hook 当成审批或沙箱。

验收标准：每个技能声明输入、输出、权限和副作用；写入、执行、恢复、删除等动作都有显式确认；禁用扩展后主系统行为与未安装扩展时一致。

### 第三阶段：MCP 安全接入

现有 MCP 管理能力应优先接只读、低权限服务器。任何会读用户数据、发送消息、改配置或执行外部命令的工具，都要由操作人员在执行前核对工具名称、数据范围和参数。当前没有通用人工审批中心；工作流 `enabled_tools` 是 allowlist，不是逐次确认。

HTTP MCP 接入应使用短期凭据、令牌受众校验和最小权限；不得把令牌写入日志、工作流 YAML、导出文件或浏览器本地存储。MCP 工具描述也应视为不可信输入，不因工具描述而自动扩大权限。

验收标准：未进入 allowlist 的工具不可由该工作流调用；权限不足时错误可解释；审计保留服务器、操作、耗时、结果和脱敏错误元数据；卸载或禁用 MCP 后工作流能给出明确降级提示。当前审计不构成跨工具的审批记录，也没有端到端 trace ID。

## 已知取舍

- WebUI 生产构建成功，但 Monaco 编辑器主包仍较大。后续应单独评估编辑器按路由延迟加载和更细粒度分包，先测量首屏与工作流编辑器实际耗时，再决定是否拆分。
- 图谱工具对 `webui/src/components/ConfigurationList.vue` 的 `script setup` 导入行给出解析告警，但 Vue 类型检查和生产构建均通过；该告警来自图谱解析器，不是已复现的运行时语法错误。
- 本项目开发时访问 Vite 根路径的 HTTP 请求必须带 `Accept: text/html` 才会进入 SPA 回退；浏览器正常访问会携带该请求头并得到页面。
