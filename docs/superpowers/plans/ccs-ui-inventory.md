本清单用于替代批量读取截图。Codex 或其他 agent 应默认阅读本文件，仅在需要视觉细节（配色、间距、栅格）时按"图片索引"一节调阅单张，每回合最多一张。

## 为什么需要这份清单

上游中转（agentrouter 等）对多图多模态请求存在概率性内容闸门，返回 `HTTP 500 sensitive words detected` 或 `HTTP 400 content-blocked`。与图片内容无关，纯随机噪声图阻断率更高。实测：

- 20 张逐个单发：0/20 阻断
- 2 张一批放入 user 消息：4/5 阻断
- 上次会话完整上下文（10 图在 tool output，3.28MB）：4/4 阻断
- 同上下文图片换文字占位（232KB）：0/4 阻断

判定结果按请求指纹缓存并粘住，原样重试永远同一结果。重试会累积失败次数，触发 CC Switch 熔断器（阈值 8 次连续失败），导致 `所有供应商已熔断` 503 并终止会话。

结论：撞到阻断不要重试，改载荷结构或跳过该张。

- 无边框自绘窗口，标题栏左侧为品牌图标 + 文字标题 `CC Switch`，右侧为最小化 / 最大化 / 关闭三键。

`通用` | `路由` | `认证` | `高级` | `使用统计` | `关于`

### 1.4 主题

每行结构：`序号圆标` + `供应商名称` + `使用中`徽章（仅当前生效者） + 右侧状态徽章。

### 2.4 自动故障转移（可折叠）

折叠头：橙色波形图标 + 标题 `自动故障转移` + 副文案「配置故障转移队列和熔断策略」+ 右侧展开箭头。

展开后顶部为信息条（i 图标，蓝色底）：

> 当故障转移队列中配置了多个供应商时，系统会在请求失败时按优先级顺序依次尝试。当某个供应商连续失败达到阈值时，熔断器会打开并在一段时间内跳过该供应商。

#### 2.4.1 重试与超时设置

| 字段 | 截图值 | 帮助文案 |
|---|---|---|
| 最大重试次数 | 6 | 请求失败时的重试次数（0-10） |
| 失败阈值 | 8 | 连续失败多少次后打开熔断器（建议: 3-10） |

#### 2.4.2 超时配置

| 字段 | 截图值 | 帮助文案 |
|---|---|---|
| 流式首字节超时 | 90 | 等待首个数据块的最大时间，范围 1-120 秒，默认 60 秒 |
| 流式静默超时 | 180 | 数据块之间的最大间隔，范围 60-600 秒，填 0 禁用（防止中途卡住） |
| 非流式超时 | 600 | 非流式请求的总超时时间，范围 60-1200 秒，默认 600 秒（10 分钟） |

#### 2.4.3 熔断器设置

| 字段 | 截图值 | 帮助文案 |
|---|---|---|
| 恢复成功阈值 | 3 | 半开状态下成功多少次后关闭熔断器 |
| 恢复等待时间（秒） | 90 | 熔断器打开后，等待多久后尝试恢复（建议: 30-120） |
| 错误率阈值 (%) | 70 | 错误率超过此值时打开熔断器 |
| 最小请求数 | 15 | 计算错误率前的最小请求数 |

底部右对齐两键：`重置`（次要样式）、`保存`（蓝色主按钮 + 磁盘图标）。

> 现场发现：内容级错误（`sensitive words detected` / `content-blocked`）当前被计入熔断器健康统计，等同于「Provider 故障」。这是请求级问题而非上游宕机，导致单个坏请求可以拖垮整条通道。kirara-ai 实现失败分类时应把「内容被拒」与「上游不可用」分开，前者不参与熔断计数。

### 2.5 整流器（可折叠）

折叠头：紫色闪电图标 + 标题 `整流器` + 副文案「自动修复 API 请求中的兼容性问题」。

三个开关项：

| 开关 | 副文案 | 截图状态 |
|---|---|---|
| 启用整流器 | 自动检测并修复 API 请求中的兼容性问题 | 开启 |
| 移除不支持的图片 | 当目标模型不支持图片时，自动移除图片内容 | 开启 |
| 纯文本模型预判 | 提前识别纯文本模型，跳过图片处理 | 开启 |

> 与本次故障直接相关：整流器已有「移除不支持的图片」能力，但触发条件是「目标模型不支持图片」。本次是「模型支持图片、中转闸门拒绝图片」，不在该判定范围内。kirara-ai 若实现同类整流器，应把「上游返回内容级拒绝」也作为图片降级的触发条件，并支持"改写载荷结构后重投"而非原样重试。

### 3.2 请求日志与统计

统计视图把三类信息分开呈现：

1. **请求日志** — 逐条请求记录，含时间、认证方式、应用分组、状态、模型、耗时、流式标记、Token 数、成本、错误信息列。状态列有 `mistake` 等标签；错误信息列直接显示上游原文（如 `sensitive words detected`）。
2. **Provider / 模型维度统计** — 按供应商与模型聚合。
3. **成本汇总** — 与定价表联动。

> 现场发现：请求日志把上游错误原文完整保留到列中，这是本次排障能定位到 `sensitive words detected` 的关键。kirara-ai 的可观测性设计应保留上游错误原文与 request id，不做归一化丢弃。
